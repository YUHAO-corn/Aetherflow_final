# AetherFlow项目入门引导补充 - 避免重复造轮子与目录混乱

本文档提供关于如何避免"重复造轮子"和"目录混乱"问题的具体指导，帮助新加入的AI编程员更有效地进行开发工作。

## 1. 避免重复造轮子

### 1.1 常见问题

许多AI编程员在未充分了解现有代码的情况下，会出现以下问题：

- **重复实现已有功能**：创建与现有组件功能重复的新组件
- **创建相似但不兼容的实现**：实现类似功能但使用不同接口或数据格式
- **忽略已有工具函数**：重新编写已在utils或服务中存在的功能
- **重复定义数据类型**：创建与现有定义几乎相同但略有差异的类型

### 1.2 代码探索流程

在开始编写任何新代码前，**必须**遵循以下流程：

1. **检查现有组件**：
   ```bash
   # 先查看基础组件
   ls extension/src/components/common
   
   # 再检查业务组件
   ls extension/src/components/{功能域}
   
   # 查看组件源码了解功能和参数
   cat extension/src/components/common/Button.tsx
   ```

2. **查找相关服务**：
   ```bash
   # 检查是否存在相关服务
   ls extension/src/services
   
   # 查看服务接口定义
   cat extension/src/services/{服务域}/index.ts
   ```
   
3. **寻找工具函数**：
   ```bash
   # 检查通用工具函数
   ls extension/src/utils
   
   # 查看具体工具实现
   cat extension/src/utils/format.ts
   ```

4. **代码搜索技巧**：
   - 使用关键词搜索整个代码库
   - 查找相似变量名和函数名
   - 检查引用关系，理解现有代码如何使用某个组件

### 1.3 实用决策树

面对新任务时，使用以下决策树确定如何行动：

```
开始新任务
└── 是否涉及UI组件?
    ├── 是 → 检查 components/ 目录中是否有类似组件
    │   ├── 有类似组件 → 复用或扩展现有组件
    │   └── 没有类似组件 → 创建新组件前先检查设计文档
    └── 否 → 是否涉及数据处理?
        ├── 是 → 检查 services/ 目录是否有相关服务
        │   ├── 有相关服务 → 使用或扩展现有服务
        │   └── 没有相关服务 → 检查是否应扩展现有服务而非创建新服务
        └── 否 → 是否是通用工具函数?
            ├── 是 → 检查 utils/ 目录是否有类似函数
            │   ├── 有类似函数 → 使用现有函数
            │   └── 没有类似函数 → 在适当的utils文件中添加新函数
            └── 否 → 继续其他检查...
```

### 1.4 具体案例分析

**案例1：需要添加按钮**
- ❌ 错误做法：直接创建新的`<button>`元素或新的Button组件
- ✅ 正确做法：检查`components/common/Button.tsx`，使用现有Button组件

**案例2：需要日期格式化**
- ❌ 错误做法：在组件中直接编写日期格式化逻辑
- ✅ 正确做法：检查`utils/`目录中是否已有日期工具，如有则使用，如无则在适当位置添加

**案例3：需要处理提示词数据**
- ❌ 错误做法：直接在组件中实现提示词存储和检索逻辑
- ✅ 正确做法：使用`services/prompt/`中的现有服务或`hooks/usePrompts.ts`中的钩子

## 2. 避免目录混乱

### 2.1 目录结构规范

AetherFlow项目采用功能域划分的目录结构：

```
extension/src/
├── components/       # 所有UI组件
│   ├── common/       # 通用UI组件
│   ├── library/      # 提示词库相关组件
│   ├── optimize/     # 优化相关组件
│   └── ...
├── services/         # 业务逻辑层
│   ├── prompt/       # 提示词相关服务
│   ├── storage/      # 存储相关服务
│   ├── messaging/    # 消息通信服务
│   └── ...
├── hooks/            # 自定义React Hooks
├── utils/            # 通用工具函数
├── types/            # 全局类型定义
├── pages/            # 页面入口
├── content/          # 内容脚本
└── background/       # 后台脚本
```

### 2.2 文件放置规则

严格遵循以下规则决定新文件的位置：

1. **UI组件**：
   - 通用UI元素 → `components/common/`
   - 特定功能组件 → `components/{功能域}/`
   - 组件文件使用PascalCase命名

2. **业务逻辑**：
   - 业务功能 → `services/{功能域}/`
   - 服务模块文件使用camelCase命名
   - 相关类型定义放在`types.ts`中
   - 服务实现放在`actions.ts`或具体文件中
   - 通过`index.ts`暴露公共API

3. **自定义钩子**：
   - 所有钩子放在`hooks/`目录下
   - 文件名使用camelCase并以"use"开头

4. **工具函数**：
   - 非业务逻辑的通用函数放在`utils/`目录
   - 按功能类型组织到不同文件中

5. **类型定义**：
   - 特定业务域的类型 → 对应服务目录的`types.ts`
   - 跨多个业务域的类型 → `types/`目录下

### 2.3 目录检查流程

开始创建新文件前，必须进行以下检查：

1. **结构熟悉**：
   ```bash
   # 浏览项目顶级目录
   ls extension/src/
   
   # 探索目标目录
   ls extension/src/{目标目录}
   ```

2. **位置确认**：
   ```bash
   # 查看类似文件的位置
   find extension/src -name "*Button*.tsx"
   
   # 检查特定功能域的现有文件
   ls extension/src/components/library/
   ```

3. **参考样式**：
   ```bash
   # 查看同类文件的命名和结构
   cat extension/src/components/library/PromptCard.tsx
   ```

4. **引用关系**：
   ```bash
   # 查看如何引用特定组件或服务
   grep -r "import.*Button" extension/src/
   ```

### 2.4 实际应用案例

**案例1：添加新的提示词卡片变体**
- ❌ 错误做法：在`src/`根目录或随意位置创建新组件
- ✅ 正确做法：在`components/library/`下创建或扩展现有的PromptCard组件

**案例2：添加日期格式化工具**
- ❌ 错误做法：在使用的组件文件中直接定义格式化函数
- ✅ 正确做法：
  - 检查`utils/`是否有dateUtils.ts
  - 如果有，在其中添加新函数
  - 如果没有，创建`utils/dateUtils.ts`

**案例3：实现新的存储功能**
- ❌ 错误做法：创建独立的存储模块或在组件中直接实现
- ✅ 正确做法：扩展`services/storage/`中的现有服务，或在协商后添加子模块

## 3. 开发前的准备工作

在开始任何开发任务前，强烈建议执行以下步骤：

### 3.1 代码库探索

1. **浏览目录结构**：
   ```bash
   find extension/src -type d | sort
   ```

2. **检查关键文件**：
   ```bash
   # 检查主要入口文件
   cat extension/src/main.tsx
   
   # 查看应用结构
   cat extension/src/App.tsx
   ```

3. **检查类型定义**：
   ```bash
   # 查看核心类型定义
   ls extension/src/types
   cat extension/src/services/*/types.ts
   ```

4. **查看现有组件**：
   ```bash
   # 列出所有React组件
   find extension/src -name "*.tsx" | grep -v "test" | sort
   ```

### 3.2 文档阅读

关注以下关键文档：

1. **项目说明文档**：`架构文档-Aetherflow/00-项目实现说明.md`
2. **组件设计文档**：`架构文档-Aetherflow/components.md`
3. **统一数据层设计指南**：`架构文档-Aetherflow/补充文档/统一数据层设计指南.md` `22-数据层设计.md`
4. **任务清单**：`架构文档-Aetherflow/51-任务清单.md`

### 3.3 实践建议

1. **先搜索，后编码**：
   - 使用代码搜索工具全局搜索关键词
   - 理解现有实现方式

2. **从简单修改开始**：
   - 先进行小的改动以熟悉代码库
   - 修改现有组件而非创建新组件

3. **遵循现有模式**：
   - 采用与现有代码一致的模式和风格
   - 保持命名约定一致性

4. **请求澄清**：
   - 对现有代码有疑问时，请直接询问
   - 确保理解任务要求和现有实现
